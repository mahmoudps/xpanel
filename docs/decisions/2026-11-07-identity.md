# Sign-in identity: security questions, OpenID Connect, root password, administrator group (2026-11-07)

Owner decisions 2026-11-06 and 2026-11-07: as cPanel, 2FA stays optional, OIDC covers panel users only and never
mailboxes.

## Security questions

cPanel's "Limit logins to verified IP addresses". Root turns the policy on; a user who set questions and signs in with
the right password from an unverified address answers them, and that address is then verified. An enrolled second
factor replaces the questions, as in cPanel. Questions are read only after the password is correct, and a wrong answer
counts against the shared sign-in lockout.

**Answers.** Normalised (NFKC, trimmed, single spaces, lower case) and stored as Argon2id hashes, so nobody can read
them. Root can only clear a user's questions (xWHM or `xpanel reset-password`, which is the recovery path and must not
leave forgotten answers in the way).

**Memory.** Measured on one core of the Ubuntu 22.04 guest with the production cost (64 MiB, 3 passes, 4 lanes), five
answers, three runs each:

| Order | Wall time | Peak process RSS |
|---|---|---|
| Parallel | 1111-1326 ms | 302 MB |
| One at a time | 1254-1554 ms | 111 MB |

On one core parallel checks gain nothing and cost a third of the 1 GB budget, so hashing and verifying run one at a
time. Every answer is still checked, so the response time does not tell which one was wrong.

## OpenID Connect

Authorization code flow only (no implicit or hybrid), PKCE S256, state and nonce per flow, a confidential client,
asymmetric ID token signatures, and full ID token validation (issuer, audience, `azp`, expiry, issue time, nonce). The
flow state is single use and bound to the browser by a `__Host-` cookie, which is the login CSRF defence, and RFC 9207
`iss` is checked when present. Provider requests refuse redirects and are bounded in time and size.

**Linking.** A provider identity signs in only after its owner linked it from their own session after confirming the
password. Nothing is matched by e-mail and no principal is created, so a provider can never take over a user. Local
two-factor authentication still applies.

**Mailboxes.** Excluded: a mailbox session needs the mailbox password for IMAP, which a provider cannot supply, so
`webmail-external-auth` is out of scope and the xMail listener does not admit these routes.

**State.** Providers, with their client secrets, live in `extended/panel/external-auth.json` (mode 0600), never in a
response or a log. Flows live in memory for ten minutes, at most 512: a restart only asks the user to start again. No
daemon or polling is added; metadata is fetched on demand and cached for ten minutes.

## Root password

`chpasswd` receives `root:<password>` on standard input, so the password never reaches an argv or a log, and the change
is reported only after the shadow entry is read back. The operator confirms their own xWHM password and any enrolled
second factor. The form scores the password as it is typed; the API applies the sign-in policy strength rule.

## Administrator group

`wheel` on EL and `sudo` on Debian and Ubuntu, read and changed with `getent` and `gpasswd`, because `/etc/group` is the
state, as in cPanel. Only active hosting accounts with a regular UID are changed. Any other member is shown and left
alone. Every change is audited before and after, and read back before it is reported.
